# AI Workflow Rules

## Approach

Build this project incrementally using a spec-driven workflow. Context files define what to build (`project-overview.md`), how it is structured (`architecture.md`), and the current state of progress (`progress-tracker.md`). Always implement against these specs. Do not infer or invent behavior from scratch.

At the start of every session: read `progress-tracker.md`, identify the first unit under **Next Up**, and implement only that unit unless told otherwise.

## Scoping Rules

- Work on one unit at a time as defined in `progress-tracker.md`.
- Prefer small, verifiable increments over large speculative changes.
- Do not combine unrelated system boundaries in a single implementation step.
- Each unit has a defined **Verify** step. Do not move to the next unit until that step passes.

## When to Split Work

Split an implementation step if it combines any two of:

- UI changes and `src/api.js` / `src/templates.js` logic changes.
- Template engine logic (`src/templates.js`) and CSV parsing (`src/csv.js`).
- Storage shape changes in `src/store.js` and feature work that reads those shapes.
- Behavior not clearly defined in `project-overview.md` or `architecture.md`.

If a change cannot be verified end to end quickly, the scope is too broad — split it.

## Handling Missing Requirements

- Do not invent product behavior not defined in the context files.
- If a requirement is ambiguous, resolve it in the relevant context file before implementing.
- If a requirement is missing, add it as an open question in `progress-tracker.md` before continuing.

## Project-Specific Rules

- **No sending.** Never add email sending, SMTP, or mailbox integration code. Phase 1 only generates text.
- **No hardcoded secrets.** API key, model name, and endpoint always come from `src/store.js` (populated via the AI Config tab). Never embed them in source.
- **All AI calls go through `src/api.js`.** No other module calls `fetch` for the AI. This isolates the proxy swap point for Phase 1.1.
- **All placeholder resolution goes through `src/templates.js`.** No other module substitutes `[Column Name]` tokens.
- **Empty cell = hard error.** If any `[Column Name]` used in the selected Subject, Body, or Prompt resolves to an empty string, throw with the message `"[Column Name] is empty in CSV for this row"`. Never silently substitute an empty string.
- **Prompt construction order.** Always: (1) evaluate conditions to select a block, (2) substitute all placeholders in Subject, Body, and Prompt, (3) send the fully substituted content to the AI. The AI must never receive raw `[Column Name]` tokens.
- **Skip rule.** If the selected block's Subject and Body are both empty after evaluation, skip the row entirely — no AI call, status = skipped.
- **Sequential only.** Rows are processed one at a time with `await`. No `Promise.all` or concurrency.
- **Key never visible.** The API key field is always `type="password"`. Never log it, display it, or include it in error messages.
- **Runs are per-row.** One `RunEntry` per successfully generated row. Never group rows into a single run object.

## Protected Files

Do not modify the following unless explicitly instructed:

- `package-lock.json` — change only via npm commands (`npm install`, `npm remove`).
- `node_modules/` and `dist/`.
- `src/test/sample.csv` — test fixture; do not edit; create a new fixture file instead.
- Third-party library internals (PapaParse, Tailwind, Vite config generated by scaffold).

## Keeping Docs in Sync

Update the relevant context file whenever implementation changes affect:

- Module boundaries or the file plan (`architecture.md`).
- localStorage key names or data shapes (`architecture.md` and `progress-tracker.md` Architecture Decisions).
- Feature scope or success criteria (`project-overview.md`).
- Completed / in-progress / next-up status (`progress-tracker.md`).

## Before Moving to the Next Unit

1. The unit's **Verify** step passes end to end.
2. No invariant defined in `architecture.md` was violated.
3. `progress-tracker.md` has been updated: the unit moved from **Next Up** → **Completed**, and the next unit is now listed as **Current Goal**.
4. `npm run build` passes (from Unit 1 onward).
